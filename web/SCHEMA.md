structureEdges semantics:
- **Shape**: three sections (`extends`/`instantiates`/`fields`), each a list of
  `[srcIdx, dstIdx]` pairs in the same topological index space as `edges`;
  each section is deduplicated and sorted by `(srcIdx, dstIdx)`.
- **Direction**: src = the extending / instantiating / field-declaring module,
  dst = the module owning the parent class / instantiated class / field
  projection — i.e. the edge points at the more foundational thing. Note the
pair order is the reverse of `edges`: structureEdges go [derived, foundational]
while `edges` pairs go [dep, importer].
- **Scope**: only cross-module pairs where **both** endpoints are alive layout
  modules survive (same filter as nodes); self-loops and unresolvable
  endpoints are dropped. Relation truth comes from extract.jsonl v3's per-record
  `module` field (compiler module index), which also covers auto-generated and
  `_private` declarations.
- **Determinism**: same inputs → byte-identical output, sections sorted as above.

Field semantics at a glance:
- `x` = |transitive dependency closure|^0.72 (left→right = foundation to apex;
  zero-closure modules are spread over the ten columns -0..-9)
- `y` = topic swimlane (band value + mean of same-topic direct predecessors within
  the column + deterministic zigzag slot)
- `r` = 0.2 + 3·√(normalized PageRank) (area ∝ foundationality)
- `closureSize` = transitive dependency count (future z-axis / abstraction-level material)
- Edge direction matches `lake exe graph` dot output: dependency → dependent
- structureEdges never enter closures/reduction; they are an independent overlay
